# Keccak and SHA-3

This directory specifies the Keccak-p permutations and the sponge functions built on them, as
standardised in FIPS 202 [FIPS 202]: the permutations Keccak-p[b, n_r] (§3), the sponge construction
(§4), the KECCAK[c] family with `pad10*1` (§5), and the SHA-3 functions (§6). The Keccak team's
reference [Keccak reference] is the design document; FIPS 202 is the normative text, and section numbers below
refer to it unless stated otherwise.

The byte-level API (`Hash/Keccak/API.lean`) provides:

- the hash functions SHA3-224, SHA3-256, SHA3-384, SHA3-512 [FIPS 202, §6.1]
  (`Hash.sha3x224` … `Hash.sha3x512`);
- the extendable-output functions (XOFs) SHAKE128, SHAKE256 [FIPS 202, §6.2]
  (`Hash.shake128`, `Hash.shake256`);
- Keccak-256 as used by Ethereum [Yellow Paper], i.e. the original Keccak submission's 256-bit hash
  (`Hash.keccak256`);
- incremental (streaming) versions of each, starting from `Hash.sha3x256Init` etc.

The reference specification (`KeccakP.lean`, `../Construction/Sponge.lean`, `SHA3.lean`) is
defined on bit strings, for every width b ∈ {25, 50, …, 1600} and any number of rounds. The fast
specification (`Fast.lean`) works on bytes and 64-bit lanes, and is proved equal to the reference
for all seven functions on byte-aligned inputs.

## Notation

Following [FIPS 202, §3.1], the state of Keccak-p[b, n_r] is a three-dimensional array of bits

$$A[x][y][z], \qquad 0 \le x, y < 5, \quad 0 \le z < w,$$

with lane size $w = 2^\ell$, $\ell \in \{0,\dots,6\}$, and width $b = 25w$. Indices $x, y$ are
taken mod 5 and $z$ mod $w$ throughout. A *lane* is the $w$ bits $A[x][y][\cdot]$, a *row*
the 5 bits $A[\cdot][y][z]$, a *column* the 5 bits $A[x][\cdot][z]$, a *slice* the 25 bits with
fixed $z$ [FIPS 202, §3.1.1]. In Lean, `Hash.Keccak.State w := Fin 5 → Fin 5 → Fin w → Bool`.

**String ↔ state** [FIPS 202, §3.1.2–3.1.3]. A $b$-bit string $S$ and the state correspond by

$$A[x][y][z] = S[w(5y + x) + z].$$

So the string is the lanes in the order $(x, y) = (0,0), (1,0), \dots, (4,0), (0,1), \dots,
(4,4)$, each lane from $z = 0$ to $z = w-1$ (`State.ofString`, `State.toString`).

**Bytes ↔ bits** [FIPS 202, App. B.1]. A byte is eight consecutive bits of a string, *least significant
bit first*: the byte `0x61` is the bit string `10000110` (`Hash.bytesToBitsLSB`). For $w = 64$,
bits $64(x+5y), \dots, 64(x+5y)+63$ of the string are bytes $8(x+5y), \dots, 8(x+5y)+7$, so lane
$(x, y)$ is the little-endian 64-bit word at byte offset $8(x+5y)$, and state bit $A[x][y][z]$ is
bit $z$ (weight $2^z$) of that word. This is the representation of `Fast.lean`, where lane
$(x, y)$ is `UInt64` index $x + 5y$.

## The permutation Keccak-p[b, n_r]

A round is $\mathrm{Rnd}(A, i_r) = \iota(\chi(\pi(\rho(\theta(A)))), i_r)$ [FIPS 202, §3.3]. All
arithmetic is over GF(2): $\oplus$ is XOR, juxtaposition is AND.

**θ** [FIPS 202, §3.2.1, Alg. 1]. XOR each bit with the parities of two neighbouring columns:

$$C[x][z] = \bigoplus_{y=0}^{4} A[x][y][z], \qquad
D[x][z] = C[x-1][z] \oplus C[x+1][z-1], \qquad
A'[x][y][z] = A[x][y][z] \oplus D[x][z].$$

Lane-wise: $D[x] = C[x-1] \oplus \mathrm{ROT}(C[x+1], 1)$, where ROT moves bit $z$ to $z+1$
(`UInt64.rotl` on little-endian lanes).

**ρ** [FIPS 202, §3.2.2, Alg. 2]. Rotate each lane: $A'[x][y][z] = A[x][y][z - r[x][y]]$. The offsets
are generated by a walk over the 24 lanes other than $(0,0)$: start at $(x, y) = (1, 0)$ and, for
$t = 0, \dots, 23$, set $r[x][y] = (t+1)(t+2)/2$ and then $(x, y) \leftarrow (y, (2x + 3y) \bmod
5)$; $r[0][0] = 0$. Offsets are reduced mod $w$. For reference, indexed by $x + 5y$:

| $y \backslash x$ | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| 0 | 0 | 1 | 190 | 28 | 91 |
| 1 | 36 | 300 | 6 | 55 | 276 |
| 2 | 3 | 10 | 171 | 153 | 231 |
| 3 | 105 | 45 | 15 | 21 | 136 |
| 4 | 210 | 66 | 253 | 120 | 78 |

These are the unreduced values of [FIPS 202, Table 2] (which prints columns in the order
$x = 3, 4, 0, 1, 2$); `Fast.lean` uses them mod 64.

**π** [FIPS 202, §3.2.3, Alg. 3]. Permute the lanes: $A'[x][y][z] = A[(x + 3y) \bmod 5][x][z]$.
Equivalently, lane $(x, y)$ moves to $(y, 2x + 3y)$ [Keccak reference].

**χ** [FIPS 202, §3.2.4, Alg. 4]. The only nonlinear step, an invertible map on each 5-bit row:

$$A'[x][y][z] = A[x][y][z] \oplus \big((A[x+1][y][z] \oplus 1)\, A[x+2][y][z]\big).$$

**ι** [FIPS 202, §3.2.5, Algs. 5–6]. XOR a round constant into lane $(0, 0)$:
$A'[0][0][z] = A[0][0][z] \oplus RC[z]$, where $RC$ is zero except

$$RC[2^j - 1] = \mathrm{rc}(j + 7 i_r), \qquad j = 0, \dots, \ell.$$

The bit $\mathrm{rc}(t)$ is the output of an 8-bit LFSR (Alg. 5): if $t \bmod 255 = 0$ it is 1;
otherwise start from $R = 10000000$ and repeat $t \bmod 255$ times: $R \leftarrow 0 \,\|\, R$;
$R[0], R[4], R[5], R[6] \mathrel{\oplus}= R[8]$; $R \leftarrow \mathrm{Trunc}_8(R)$; output
$R[0]$. Equivalently, $\mathrm{rc}(t)$ is the constant term of $x^t \bmod (x^8 + x^6 + x^5 + x^4 + 1)$
over GF(2) [Keccak reference, §1.2]. For Keccak-f[1600] the 24 constants, as 64-bit words with bit $z = RC[z]$,
are `0x0000000000000001`, `0x0000000000008082`, `0x800000000000808A`, … `0x8000000080008008`
(the full table is `Hash.Keccak.roundConstants`).

**Keccak-p and Keccak-f** [FIPS 202, §3.3, Alg. 7; §3.4]. Keccak-p[b, n_r] converts the string to a
state, applies $\mathrm{Rnd}(\cdot, i_r)$ for

$$i_r = 12 + 2\ell - n_r, \;\dots,\; 12 + 2\ell - 1,$$

and converts back. These are the *last* $n_r$ rounds of the $12 + 2\ell$ rounds of
Keccak-f[b] = Keccak-p[b, 12 + 2ℓ]. FIPS 202 uses only Keccak-f[1600] = Keccak-p[1600, 24]
($\ell = 6$, $w = 64$, $i_r = 0, \dots, 23$).

| ℓ | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| $w$ | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
| $b$ | 25 | 50 | 100 | 200 | 400 | 800 | 1600 |
| rounds of Keccak-f[b] | 12 | 14 | 16 | 18 | 20 | 22 | 24 |

The ρ offsets and the round constants are written in `Constants.lean` as tables and proved equal
to the derivations above by kernel computation (`Hash.Keccak.rhoOffsets_eq`,
`Hash.Keccak.roundConstants_eq`).

## The sponge

SPONGE[f, pad, r] [FIPS 202, §4, Alg. 8; BDPV 2007] turns a permutation $f$ of $b$-bit strings into a function
from a bit string $N$ and an output length $d$ to $d$ bits. The state is split into the *rate*
$r$ and the *capacity* $c = b - r$.

1. Pad: $P = N \,\|\, \mathrm{pad}(r, |N|)$, and split $P$ into $r$-bit blocks $P_0, \dots, P_{n-1}$.
2. Absorb: $S \leftarrow 0^b$; for each block, $S \leftarrow f(S \oplus (P_i \,\|\, 0^c))$.
3. Squeeze: $Z \leftarrow \mathrm{Trunc}_r(S)$; while $|Z| < d$, $S \leftarrow f(S)$ and
   $Z \leftarrow Z \,\|\, \mathrm{Trunc}_r(S)$. Return $\mathrm{Trunc}_d(Z)$.

Algorithm 8 thus produces $\max(1, \lceil d/r \rceil)$ output blocks.

**`pad10*1`** [FIPS 202, §5.1, Alg. 9]. For a message of $m$ bits and block size $x$,

$$\mathrm{pad}(x, m) = 1 \,\|\, 0^j \,\|\, 1, \qquad j = (-m-2) \bmod x,$$

so that $m + j + 2$ is a positive multiple of $x$. At least two bits are always added.

**KECCAK[c]** [FIPS 202, §5.2] = SPONGE[Keccak-p[1600, 24], `pad10*1`, 1600 − c]
(`Hash.Keccak.Reference.keccak`).

## Instances

Each function appends a domain-separation suffix to the message $M$ and calls KECCAK[c]
[FIPS 202, §6.1–6.2]. Security strengths are in bits [FIPS 202, App. A.1, Table 4]; $d$ is the output length.

| Function | $r$ (bits / bytes) | $c$ | Suffix | Output | Collision | Preimage | 2nd preimage |
|---|---|---|---|---|---|---|---|
| SHA3-224 | 1152 / 144 | 448 | `01` | 224 | 112 | 224 | 224 |
| SHA3-256 | 1088 / 136 | 512 | `01` | 256 | 128 | 256 | 256 |
| SHA3-384 | 832 / 104 | 768 | `01` | 384 | 192 | 384 | 384 |
| SHA3-512 | 576 / 72 | 1024 | `01` | 512 | 256 | 512 | 512 |
| SHAKE128 | 1344 / 168 | 256 | `1111` | $d$ | $\min(d/2, 128)$ | $\ge \min(d, 128)$ | $\min(d, 128)$ |
| SHAKE256 | 1088 / 136 | 512 | `1111` | $d$ | $\min(d/2, 256)$ | $\ge \min(d, 256)$ | $\min(d, 256)$ |
| Keccak-256 | 1088 / 136 | 512 | none | 256 | — | — | — |

Keccak-256 is not a FIPS 202 function: it is KECCAK[512]$(M, 256)$ with the original Keccak
padding and no suffix [Keccak reference; Yellow Paper], and its output differs from SHA3-256. (Its generic bounds are those
of SHA3-256, having the same $c$ and $d$, but FIPS 202 lists no strengths for it.) The SHAKE
suffix `1111` is the RawSHAKE suffix `11` followed by `11` [FIPS 202, §6.3].

**Bytes on the wire** [FIPS 202, App. B.2]. For a byte-aligned message, the suffix and the first
padding bit fill the low bits of the next byte (LSB first), and the last padding bit is the top
bit of the last byte of the block:

| Function | Bits after $M$ (LSB first) | First pad byte | Last pad byte | If only one byte remains |
|---|---|---|---|---|
| SHA3-* | `01` `1` `00000` | `0x06` | `0x80` | `0x86` |
| SHAKE* | `1111` `1` `000` | `0x1F` | `0x80` | `0x9F` |
| Keccak-256 | `1` `0000000` | `0x01` | `0x80` | `0x81` |

In between are zero bytes. `Fast.pad` implements exactly this, and
`Hash.Keccak.Equiv.bytesToBitsLSB_pad` proves it equal to $M \,\|\, \text{suffix} \,\|\,
\mathrm{pad}(r, |M| + |\text{suffix}|)$ on bits; `domainByte_sha3`, `domainByte_shake` and
`domainByte_keccak` check the three bytes.

## Security notes

- *Generic security.* A sponge on a random permutation is indifferentiable from a random oracle
  up to about $2^{c/2}$ queries [BDPV 2007; BDPV 2008]; Almeida et al. give a machine-checked proof in EasyCrypt
  [Almeida et al. 2019]. The strengths in the table above are $\min$ of the output-length and $c/2$ bounds
  [FIPS 202, App. A.1].
- *No length extension.* Only the rate part of the state is output; the capacity is never
  revealed, so the length-extension property of Merkle–Damgård hashes does not apply.
- *XOF outputs.* SHAKE outputs for different $d$ are prefixes of one another (proved below), so
  $d$ is not a domain separator: SHAKE128$(M, 256)$ begins with SHAKE128$(M, 128)$ [FIPS 202, App. A.2].
- *Reduced rounds.* Practical collision attacks exist on round-reduced instances (up to 6 of the
  24 rounds for some Keccak instances) [Guo et al. 2020]; none reaches the full 24 rounds.

Scope and limits. The fast specification takes byte strings, so messages whose length is not a
multiple of 8 bits are covered only by the reference. The equivalence is proved for the five
rates 72, 104, 136, 144, 168 bytes (`Equiv.Rate`). The streaming interface is not proved equal to
the one-shot functions; it is tested against them on the NIST CAVP vectors split at several
points (`HashKAT/`) and by fuzzing (`harness/`).
